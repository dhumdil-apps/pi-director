Instruction system

Lifecycle branches

The runtime persists mode only after a User action. The Agent recommends routes but never chooses one; the mode picker, native Ask direct routes, and commands are the transition surfaces.

Complete operational pseudocode

This consolidates the behavior distributed across the instruction files. Follow the source links for the exact Markdown text and API field documentation.

1. Bootstrap, prompt assembly, and transitions 
ON before_agent_start(event, context):
    IF context.hasUI is false:
        RETURN original system prompt                 // headless bypass

    mode := latest persisted MODE_EVENT OR QUESTIONNAIRE
    IF no persisted mode:
        persist QUESTIONNAIRE                         // only the User later changes it

    IF session has no named artifact:
        create one timestamped plan from plan-template.md
        insert runtime-owned timing block

    inject constant pi_workflow prompt:
        workflow-steps.md + agent-guidance.md + agent-api.md
    inject current mode marker

ON User selects picker action or native-Ask direct route:
    persist selected mode
    start matching continuation with pending plan context

ON /questionnaire:
    persist QUESTIONNAIRE
    wait for the next User message

ON /spec or /vibe:
    persist selected mode
    start the extension-generated continuation with pending plan context

// Agent recommendation records available actions; it never changes mode

ON /handoff [name]:
    run outgoing CHECKPOINT only
    preserve the same artifact
    start replacement session in QUESTIONNAIRE

ON turn settlement:
    runtime opens the picker
    use Agent recommendations for this turn when present
    OTHERWISE, while work remains, offer contextual continuation fallback
    return completed work to the editor
2. Q&A — alignment mode 
MODE QUESTIONNAIRE:
    ON first session request:
        CALL start_task once
        state understood goal and scope
        ASK one concise direction-check question
        write answer and direction check to artifact

    BEGIN every interaction with native ask; never ask inline
    ask focused goal, scope, constraint, trade-off, and outcome questions
    use 1..4 independent questions with confidence-ranked concrete options
    use customAnswerLabel when free-form detail is required
    do not research source or report research results
    only read bounded orientation from relevant .pi, README, or docs

    ON instruction that adds, conflicts with, or appears to replace scope:
        keep initial goal and every pending checklist outcome visible
        ask whether each affected outcome stays, defers, or resolves
        never silently rewrite or remove historical scope

    AFTER every completed Ask:
        copy prompt, context, displayed options, and selected/custom answer to Q&A transcript
        record concise interpretation in Align

    WHILE alignment remains unresolved:
        ask the next focused question
        IF User cancels: return to editor

    IF direction is clear and low risk:
        recommend Vibe
    ELSE:
        recommend Spec

    IF User explicitly proceeds with best to Spec or Vibe:
        target turn first records all accepted best-confidence answers
3. Spec — research and proposal mode 
MODE SPEC:
    explore using focused-evidence procedure
    update Current state, Findings, Desired state, Approach, and Checklist
    prefer smallest sufficient change; name rejected alternative

    IF blocked:
        record problem, options, and recommendation in artifact
        recommend Q&A
        stop unless the remaining proposal is independently actionable

    IF research remains:
        recommend continuing Spec
        end turn

    CALL save_plan with complete actionable proposal
    end turn                                         // save_plan presents the proposal

FOCUSED-EVIDENCE PROCEDURE:
    begin with one exact symbol or path search
    bound matches and line width
    read owning implementation in small windows
    exclude dependencies, generated/vendor/cache trees, and source maps
    stop when answered; broaden only for a concrete unresolved question
4. Vibe — execution, blockers, and close-out 
MODE VIBE:
    resolve implementation research in place
    implement scope
    run repository-owned useful checks
    report pre-existing failures without widening scope
    update Work log and cumulative Checklist

    FOR each reversible, low-risk, in-scope choice already implied by task:
        decide autonomously
        CALL record_auto_decision with rationale, impact, and verification

    IF genuine decision blocker:
        record the problem
        CALL native ask once with direct resolution, broader Q&A, and known alternatives
        IF User resolves directly: continue Vibe
        IF User requests broader alignment: CHECKPOINT; recommend Q&A
        OTHERWISE follow the selected route

    IF scope remains:
        CHECKPOINT
        IF coherent phase boundary:
            record completed boundary and first pending item
            recommend phase handoff
        ELSE:
            recommend Vibe continuation
    ELSE:
        CLOSE_OUT
        IF no review-worthy autonomous decisions, limitations, or follow-up concerns:
            do not call recommend_next; task is complete

PROCEDURE CHECKPOINT:
    reconcile initial goal, accepted proposals, follow-ups, and all revisions against live checklist
    review every Auto-mode decision and its verification details
    mark completed historical checklist labels without renaming them
    leave skipped/failed work pending with a reason
    preserve historical narrative; update only live status
    write Close out Status = in progress
    report paths, verification, limitations, and concerns
    promote only durable, costly orientation/quirks to project memory

PROCEDURE CLOSE_OUT:
    CHECKPOINT
    IF any requested outcome or autonomous decision is unresolved:
        leave it pending; do not claim completion
    ELSE:
        write Close out Status = complete
        recommend Q&A only for review-worthy decisions, limitations, or follow-up concerns
5. Artifact, API, and cross-cutting constraints 
ARTIFACT INVARIANTS:
    one session owns one .pi/plan/<name>.md; plan files are never deleted
    start_task names it once; a different later name is refused
    Goal and accepted outcomes remain historical scope across handoffs and revisions
    Checklist is cumulative; latest checkbox state wins
    save_plan belongs only to Spec:
        replace untouched pre-execution draft
        otherwise append dated Revision N while preserving history
    execution locks the plan name

NATIVE ASK CONTRACT:
    asks are mode-neutral but do not change User-owned mode by ordinary answer
    Vibe uses Ask only for a genuine blocker
    questions contain stable id, context, prompt, 2..4 options, and confidence 1..5
    batch only independent questions; ask dependent follow-ups in a new call
    direct routes preserve manual answers and accept remaining highest-confidence answers

OTHER TOOL AND OUTPUT RULES:
    recommend_next records actions; it does not select a mode
    match every operation to its tool schema; correct one rejected call and retry once
    size work and plan to the change; lead with result; name paths and symbols
    show changed snippets, do not repeat transcript output or claim unrun checks
    preserve safeguards for destructive actions, dependencies, credentials, and external writes
